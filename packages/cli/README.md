# cli

Export Jira Data Center configuration with the `jira-config-export` command. The exporter uses the [jira](../jira/README.md) API client; keep credentials out of source control.

From the repository root, put a `jira-dc` entry with `url`, `user`, and `password` in the ignored `.scratch/app-credentials.yaml`, then run:

```sh
uv run jira-config-export doctor          # check config, DNS, TCP, TLS, credentials
uv run jira-config-export export ./export # run the export (add -v for debug logs)
```

`doctor` runs these checks in order and stops at the first failure, marking later checks `skip`: `config` (credentials file loads), `url` (scheme/host/port), `dns`, `tcp` (connect), `http` (TLS and routing, via unauthenticated `GET /rest/api/2/serverInfo`), `auth` (`GET /rest/api/2/myself` with Basic auth), and `proxy`. `proxy` warns when `HTTPS_PROXY`-style variables are set, because the exporter's explicit httpx transport ignores them (curl would not). Output never includes the password or response bodies. `doctor` exits nonzero if any check fails; warnings alone do not.

`export` prints, in order: a one-line **preflight** (the `doctor` checks for config, network, and credentials; a failure stops the run before the output directory is touched and points you at `doctor`), the **output directory** as an absolute path, the **run state** (a fresh export, or which stages are complete, partial, failed, or still to do when resuming), and then each stage with **one dot per record written**. A stage resuming part-way shows `(N already written)` before its dots, and stages that are already complete show a `Skipping` line. When Jira answers 429 (rate limited), the wait is shown inline as `(wait:30s)` in the dots line, then the request is retried up to 3 times. Requests are paced evenly at `REQUESTS_PER_MINUTE` (120, near the top of `cli/main.py`; edit it to go faster or slower). The preflight and `doctor` make a handful of requests outside this pacing.

This uses HTTP Basic authentication. The command writes `./export/fields.jsonl` (one custom field per line), `manifest.json`, and `checkpoint.json`, then prints styled progress, the field count, and a color-coded coverage table using Rich. Typer provides argument validation and `--help`. The field inventory uses `GET /rest/api/2/field`; system fields are excluded. Other read-only configuration endpoints are described below. A failed request exits nonzero and records a safe failure status without replacing an existing field export. Rerun with the same directory to skip a completed field stage or resume an incomplete/failed one. The manifest has schema version, run ID, creation timestamp, unknown Jira/app version placeholders, and stage coverage; the checkpoint has stage status, count or safe error type and HTTP status. App versions are not queried yet.

`fields.jsonl` comes from a single request, so it is written to a temporary file in the destination directory, flushed and synchronized, then atomically replaced. Every other stage appends to its JSONL file as data arrives, in resumable units: one page of results (`field_contexts`, `screens`), or one custom field, screen, or tab (`custom_field_options`, `screen_tabs`, `screen_tab_fields`). After each unit the CLI appends whole lines, flushes and `fsync`s the file, then atomically records `{cursor, offset, count}` for the stage under `progress` in `checkpoint.json`. A crash or Ctrl-C therefore keeps every committed unit; bytes past the recorded `offset` (a torn final line, or a unit whose checkpoint was never saved) are truncated on the next run, so nothing is duplicated and no partial line survives a resume. Rerun with the same directory to resume a failed or interrupted stage from its cursor without refetching committed units; completed stages are skipped. If the file no longer matches the recorded progress, the stage restarts from the beginning and replaces its file. Duplicate source IDs within a stage are written once, with the first occurrence winning. Run this on a local filesystem with directory `fsync` support; concurrent writers to one output directory are not supported.

**A stage's file is only complete when its status is `complete`.** A stage that failed part-way leaves its committed records in place and reports `records_written` in `checkpoint.json` and `manifest.json`; downstream tools must check `manifest.json` coverage rather than assuming a file's presence means a full export. A stage that fails before producing anything leaves no file. Records appear in the order Jira returned them (only `fields.jsonl` and each page or unit's own records are sorted by ID), so sort downstream if you need a global order.

**Project → issue type → workflow → screen inventories.** Five more stages are resumable and checkpointed like the others. `projects` (`projects.jsonl`, from `GET /rest/api/2/project?includeArchived=true`; records carry key, name, type, and an `archived` flag) and `issue_types` (`issue-types.jsonl`, from `GET /rest/api/2/issuetype`) make the numeric IDs in other files readable. `issue_type_schemes` (`issue-type-schemes.jsonl`) writes one record per scheme with its `issue_type_ids`, `default_issue_type_id` (`null` when the scheme has no default), and `project_ids`: each scheme costs two requests, `GET /rest/api/2/issuetypescheme/{id}?expand=issueTypes,defaultIssueType` (Jira returns the issue types and the default issue type only when asked; the `expand` parameter is missing from the bundled spec, so the client declares it) and `GET .../associations`. Only project IDs are kept from association records; leads, roles, versions, and components are not copied. `project_workflow_schemes` (`project-workflow-schemes.jsonl`) writes one record per project from `GET /rest/api/2/project/{key}/workflowscheme`, keyed by project ID because schemes can be shared; `issue_type_mappings` maps issue type IDs to workflow names, and issue types absent from it use `default_workflow`. It requires `projects`; if that stage is incomplete it is reported `not_queried`. A project that has no workflow scheme or cannot be read fails the stage rather than being written as empty, and the stage resumes at that project on rerun.

`project_issue_type_view_screens` (`project-issue-type-view-screens.jsonl`) writes one record per project and per issue type its issue type scheme offers: the screen used for **viewing an issue**, with `screen_id` (which joins to `screens.jsonl`), `screen_name`, `state`, and the IDs of the projects and issue types that share the screen. It requires `projects` and `issue_type_schemes`. **This stage reads Jira's internal project-settings API** (`GET /rest/projectconfig/1/issuetype/{projectKey}/{issueTypeId}/fields`), which is not part of the documented REST API and may change between versions, so its results carry `"api": "internal"` in `checkpoint.json` and `manifest.json`. Only the View screen is exposed: the Create and Edit screens, the screen schemes behind them, and per-field settings (hidden, required) have no read route in either the public or the project-settings API.

Together with the screen files, these let you trace **project → issue type → view screen → tabs → fields** and **project → workflow**. They cannot trace which screens a project's issue types use for Create or Edit.

The CLI also queries the Jira DC 11.2.1 `GET /rest/api/2/customFields` inventory for field-level project/issue-type applicability (`custom-fields.jsonl`) and `GET /rest/api/2/customFields/{numericId}/options` with `useAllContexts=true` for option IDs/values (`custom-field-options.jsonl`). These are independently checkpointed stages: a failed or interrupted stage resumes from its last committed unit; completed stages are retained. Option source IDs combine the field ID and option ID. The applicability data is **not** an explicit context record: the bundled DC API does not expose context IDs, field configurations, or field configuration scheme associations. Field configurations (per-field hidden/required settings) are **not collected and not listed in the manifest**: the only related route Jira publishes, `/rest/projectconfig/1/issuetype/{project}/{issueType}/fields`, returns just the view screen (see above). Custom field contexts (Jira's internal `FieldConfigScheme`) are **not collected and not listed in the manifest**: the bundled spec defines the bean but no route, `GET /rest/api/2/field/{id}/configschemes` returns 404 on Jira DC 11.3.12, and the route lists that instance publishes (`application.wadl` for `/rest/api/2` and `/rest/projectconfig/1`) contain nothing for contexts. For queried stages, unauthorized (401/403), unsupported (404/405/501), and failed results are recorded separately in checkpoint and manifest without copying the response body. Screen inventory, tabs, and tab fields are also independently checkpointed in `screens.jsonl`, `screen-tabs.jsonl`, and `screen-tab-fields.jsonl` using the supported `GET /rest/api/2/screens` (paginated), `/screens/{screenId}/tabs`, and `/screens/{screenId}/tabs/{tabId}/fields` endpoints. Records link screen, tab, and field IDs; `position` is the zero-based response-list order. Screen schemes and issue type screen schemes are likewise **not collected and not listed in the manifest**: neither the bundled spec nor the route lists published by a Jira DC 11.3.12 instance contain a read route for them. Failed or unauthorized screen requests do not become empty files; dependent stages are `not_queried` until the prerequisite succeeds. ScriptRunner configuration is likewise marked `unsupported`: the vendor documents a Script Registry browser ZIP export (8.54+, 9.19+, 10.0+) and a built-in Configuration Exporter script, but no supported read-only configuration REST API was identified. No ScriptRunner endpoint is guessed, no association file is emitted, and this status must not be read as zero matches. Elements Connect configuration is also marked `unsupported`: its [REST API guide](https://doc.elements-apps.com/elements-connect/elements-connect-rest-api) describes rendering field content, while its [field configuration guide](https://doc.elements-apps.com/elements-connect/field-configuration) documents an admin/browser JSON export, not a supported read-only configuration API. The CLI does not guess an endpoint or infer associations from field names; no Elements Connect file is emitted. The CLI prints per-stage progress and a final coverage summary: `complete (0 records, not found)` means a successful empty query, while `not_queried`, `unsupported`, `unauthorized`, and `failed` identify gaps. It reads Jira's version from `GET /rest/api/2/serverInfo` when accessible; unknown app versions remain absent from `app_versions`. A failed or unauthorized queried Jira stage, including a 404/405/501 unsupported response, exits nonzero while preserving successful output for retry. Known missing Jira/app APIs reported as static `unsupported` gaps are advisory and do not alone make every run fail. Treat all exports as sensitive.

Each line is a schema version 1 record, for example:

```json
{"extracted_at":"2026-10-29T00:00:00+00:00","field":{"name":"Team"},"schema_version":1,"source":{"endpoint":"/rest/api/2/field","entity":"field","id":"customfield_10001","system":"jira"}}
```

`source.system`, `source.entity`, and `source.id` identify the source record; `source.endpoint` names the read-only API, and `extracted_at` is the UTC time of this export. The exporter sorts fields by Jira ID and JSON keys lexicographically. Only the field name is retained: other source properties (including descriptions and app metadata) are omitted rather than copied verbatim. Names containing credential assignments such as `password=...` are replaced with `[REDACTED]`. This does not guarantee detection of arbitrary secrets embedded in ordinary names; review and protect output files as sensitive configuration data.
